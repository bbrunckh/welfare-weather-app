### 10.1 Git-backed Posit Connect deployment (config as of 2026-09-02; commits `0b73a4c`, `459d3f7`, `fdd3960`)

- Connect pulls straight from this GitHub repo (poll or "Update Now") instead of a push-button `rsconnect::deployApp()` bundle. This requires a committed root `manifest.json`; `app.R` runs via `pkgload::load_all()` because `wiseapp` is never installed into the Connect library.
- **Regenerating the manifest:** whenever dependencies or the shipped file set change, run in `dev/03_deploy.R`: `rsconnect::writeManifest(appDir = ".", appFiles = c("app.R", "R", "inst", "man", "DESCRIPTION", "NAMESPACE"), appPrimaryDoc = "app.R")`, then **rewrite the `Repository` field of `sf`, `terra` and `geojsonsf` to the PPM centos8 binary repo** (`https://packagemanager.posit.co/cran/__linux__/centos8/latest`) and commit. ⚠️ **2026-09-02 correction — do not strip them.** The earlier instruction to re-strip `sf`/`terra`/`geojsonsf` was wrong for `mapgl`: it hard-Imports all three in both its `DESCRIPTION` Imports *and* its NAMESPACE (`import(sf)`, `import(terra)`, `import(geojsonsf)`), so the stripped manifest fails `R CMD INSTALL` of mapgl on Connect ("dependencies 'geojsonsf', 'sf', 'terra' are not available for package 'mapgl'"), and mapgl could not be loaded at runtime without them anyway. The pre-mapgl strip was only ever safe by accident: leaflet lists `sf (>= 0.9-6)` in Imports, but its NAMESPACE merely registers S3 methods for sf classes (no `import(sf)`), and packrat kept restoring the library installed by the earlier push-button deploys rather than re-running the dependency check — the first genuinely new install (mapgl) exposed the gap. Since the Connect host lacks GDAL/GEOS/PROJ headers for source builds, the three entries must point at PPM's centos8 **binary** repo (the URL Connect already configures). The binaries still need the GDAL/GEOS/PROJ **runtime** libraries (EPEL 8) at load time — `terra` 1.9-11 has shipped in every committed manifest and deployed fine, so the stack is believed present; a `libgdal.so`/`libgeos.so` "cannot open shared object" failure at install means the Connect admins must add the runtime libraries (no mapgl deployment is possible without them). Verify with `jq -r '.packages | keys[]' manifest.json | grep -cxE 'sf|terra|geojsonsf'` → `3` (and `.packages.sf.Repository` → the centos8 URL), then commit the diff.
