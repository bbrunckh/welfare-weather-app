## 0. How to read this report

**IDs.** Findings carried over from the previous report keep their `CR-` id so the status can be followed (`CR-SEC-01` …). New findings use `R2-` (`R2-SEC-01` …). The full status of every old id is in Appendix A.

**Severity:** Critical · High · Medium · Low · Info. **Effort:** S (< 1 day), M (1–3 days), L (> 3 days).

**Evidence:** *measured* (real BFA data in this container), *prototype-measured* (a change tried in the scratch directory only, with an equivalence check; not shipped), *offline test* (synthetic data or fake values, no network), *code reading*.

**Status vs previous report:** new · still present · changed · fixed.

**Line numbers** refer to `df37cdb`.

**Data protection.** Only aggregates, timings and memory figures appear here. No household-level values, ids or small cells; no credentials.

**Security write-ups** stay at the level of risk, location and remediation. Nothing was exercised against real infrastructure.

## 1. Executive summary

Since the previous report the code has moved a long way: Step 2 now runs on a mirai worker with atomic, checksummed result artifacts; the Step 3 decomposition context is built once per run; the RIF and welfare-statistics kernels were optimised; Step 1–3 tables and charts are on reactable/echarts4r; several old bugs are fixed. The test suite is large (925 `test_that` blocks, 6,473 passing expectations) and the core numerics are well characterised.

Running the app on real data, though, shows four things the static review could not:

1. **The deployment is likely broken as committed** (R2-OPS-01/02/03/05). The UI needs `brand.yml` and the Step 3 decomposition tab needs `DT`; neither is declared or in `manifest.json`. Rendering the page fetches the brand's Google font; with that host unreachable, every request failed here. The bundled DuckDB `httpfs`/`spatial` binaries only load on duckdb 1.5.5, which is not pinned.
2. **Several headline numbers are biased, and the bias is measurable on BFA.** The CMIP6 baseline understates near-term warming by 12–18% and the projected welfare loss and poverty increase by about 10% (CR-BUG-01). RIF + LCU assigns every household to the 10th percentile (CR-BUG-02). The median's coefficient uncertainty is 0.18× its Monte Carlo value (R2-BUG-03). The async Step 2 path builds the anomaly reference over the wrong years when the historical window does not end in 2020 (R2-BUG-01).
3. **Most of the remaining time is on the main R process, and it scales badly.** For BFA's 3 SSP × 3 period case, the worker needs 4.8–6 minutes and 6.8 GB, the result artifact is 0.5–1 GB, and back on the main process a poverty-line change in Step 2 Results blocks for 61 s, a Step 3 run for 47 s, and every Step 3 aggregation-method switch for ≈105 s. BFA is the *small* payload.
4. **The security issues from the previous report are still open**, and one new path makes them worse: the Step 2 worker fills credentials from the server environment for a session-chosen host (R2-SEC-01).

### 1.3 What is good (keep it)

- **Async and artifacts.** One local mirai daemon with a dispatcher memory cap and `onStop()` teardown; atomic, checksummed `qs2` artifacts in per-job 0700 directories; progressive partial results; generation and signature checks before adoption.
- **Numerics.** The Rcpp welfare kernel and the RIF changes from the tracking log hold up; weighted Gini paths agree exactly; mean, poverty and Gini delta-method SDs match Monte Carlo on real data (0.94–1.02); the policy decomposition identity (total = main + repositioning + interaction) holds per row.
- **Caches that work.** Overview metadata (2.2 s → 0.01 s), the weather disk caches for historical runs (12.7 s → 1.3 s), the decomposition context built once per run (its remaining cost is ≤ 0.03 s).
- **UI layer.** reactable with client-side CSV and echarts4r on screen almost everywhere; the hexmap bridge with pinned, hash-checked vendored assets.
- **Engineering hygiene.** Business logic in `fct_*`, characterisation tests, no `TODO`/`%>%`, SQL escaping, credential redaction in exports and provenance, deterministic seeding (`wise_seed()`).

## 2. Environment, access checks and what was run

### 2.1 Container setup (differences from the brief)

- **R was not installed** in the container. I installed R 4.5.3 from Posit's CDN (`r-4.5.3_1_amd64.deb`) with `dpkg --force-depends`, because the Ubuntu archive is blocked by the network policy.
- Package binaries came from Posit Package Manager (`p3m.dev`, noble) after the user allowed `rspm-sync.rstudio.com`. Versions are "latest" (6 October 2026), so a few differ from `manifest.json` (duckdb 1.5.6 vs 1.5.5, glmnet 5.1 vs 5.0, parsnip 1.6.1 vs 1.6.0).
- The `igraph` binary needs the system library `libglpk.so.40` (not installable without the Ubuntu archive). I built `libglpk.so.40` from the GLPK sources vendored inside igraph's own CRAN tarball, into `/usr/local/lib` of the container only; `igraph::components()` (the only igraph function the app uses) was verified.

- `WISEAPP_DATA_SOURCE` was not set (only the `DATABRICKS_*` variables); scripts used `build_connection_params("databricks")`, which is what auto-connect does.

## 4. Bugs and correctness

Ordered by severity. "Synthetic" means an offline test with made-up data; "measured" means real BFA data (aggregates only).

### 4.1 High

#### CR-BUG-01: CMIP6 baseline is a mean of two climatologies (High, effort S) — still present, **measured**

**Where:** `fct_get_weather.R:1383-1385` (baseline window = range of the historical simulation dates), `:1499-1527` (historical-file climatology), `:1582-1594` (SSP-file climatology, then `union_all()` + `mean()`), `:1647-1653`.

**What.** The historical CMIP6 file stops in 2014 and the SSP files start in 2015 (checked on the BFA files: historical 1950–2014, 30 models; SSPs 2015–2100, 22–27 models, 174 H3 cells). Each part is first reduced to a monthly climatology, then the two climatologies are averaged with equal weight. With the default 1991–2020 window, the six SSP years get 50% of the weight instead of 20%. Neither part is clipped at the 2014/2015 boundary, so overlapping years would be double-counted.

**Measured on BFA (grid-cell × month × model level, default window 1991–2020):**

#### R2-BUG-02: One missing prediction silently zeroes coefficient uncertainty (High, effort S) — new, synthetic + measured counts

**Where:** `fct_aggregation_delta.R:126-131` (`F_agg <- NULL` when any gradient is non-finite → `var_coef = 0`); preparation drops only NA `y_point` (`:457`), not NA weights or NA factor-loading rows.

**What.** Any non-finite gradient — from an NA weight, an NA factor-loading row (unseen fixed-effect level, NA control in the baseline survey, NA weather from a partial CMIP6 member, CR-BUG-06), or an `exp()` overflow — sets the coefficient variance of the **whole** aggregate (mean, median, Gini, poverty) to zero, while the point estimate is still shown. #### R2-BUG-03: Median delta-method gradient is wrong, so median coefficient uncertainty is close to zero (High, effort S) — new, synthetic + **measured**

**Where:** `fct_aggregation_delta.R:275-298`.

**What.** The gradient uses the Hampel influence function `w̃ (0.5 − 1{μ ≤ m}) / f(m)` with no `μ_i` factor. That is the sampling-variance influence function, not ∂m/∂log yᵢ: under a common shift of every household's log welfare the gradients sum to about zero, although the median moves by m·δ. Synthetic: delta-method SD / Monte Carlo SD = 0.00 (intercept-like loading), 0.40 (correlated), 0.00 (mixed); mean, poverty and Gini paths match Monte Carlo (ratios 0.97–1.01). **Measured on real BFA pipelines** (OLS, default scenario; 2 pipelines × 4 years; 400 Monte Carlo draws of β through `F_loading`): delta-method SD / Monte Carlo SD = **0.18** for the median (0.17–0.19), against 0.98 for the mean, 0.94 for the poverty headcount and 1.02 for the Gini. The median's coefficient band is about 5.7× too narrow.

**Fix.** Smoothed-quantile derivative `kᵢ = w̃ᵢ φ((m − μᵢ)/b)/b`, `hᵢ = kᵢ μᵢ / Σk` (synthetic: 0.199 vs 0.209 and 0.325 vs 0.343 against Monte Carlo). This affects the median rows of the threshold table, the uncertainty bars, contrast SDs and the Step 3 decomposition (shared code).

#### R2-BUG-06: RIF repositioning uses the absolute weather level (High for RIF, effort M) — new, synthetic

**Where:** `fct_policy_metric_decompose.R:51-66, 192-203`; `fct_policy_decompose.R:232-266`; compare Step 2's anchoring `fct_rif_sim.R:509-515, 610-627`.

**What.** Step 2 RIF predictions are anchored to observed welfare, `y_t = y_obs + β(τ)(W_t − W_svy)`. **Fix.** Subtract each household's survey-time weather in the products (for bins, the difference of category contrasts); add a parity test against `predict_rif`.

#### CR-BUG-08: Policy lever gating uses substring matching and picks the wrong coefficient (High, effort S) — still present, upgraded

## 5. Performance (backend first)

### 5.1 Method and what is blocking

All numbers are **measured on real BFA data** (2 waves, 14,186 households; baseline wave 7,128 households) read from Databricks, in this container (§2). Medians of 2 repetitions (3 for Step 1); every repetition is a fresh R process. "Cold" = empty weather disk cache (raw slices, `h3_weights`, location-month tables) and a new Databricks token; "warm" = second run with the cache filled. Peak RSS is the whole process tree, sampled every 0.25 s from `/proc`. Step 2 was driven through the production worker entry point (`step2_async_worker()` → `step2_compute()` → `fct_run_simulation()`), in-process, with stage timers attached by `trace()`; the repository harness was not used for Step 2 timings because it now mislabels weather vs pipeline time (R2-OPS-08). Default app settings unless stated: weather variables `t` and `spei6` (continuous, 1–3 month lags), interaction `urban`, fixed effects `year` + `gaul1_code`, LASSO covariates, cluster `loc_id_panel`, historical window 1991–2020, residuals "original" (OLS) / "none" (RIF), coefficient uncertainty on.

| Overview metadata (cache miss) | mirai worker | No |
| Survey load, H3 map, panel (`mod_1_02`) | Main process | **Yes** |

What the numbers say:

1. **Weather dominates every Step 2 workload** (63% of the 3×3 cold run, 72% of the default scenario cold run), and **the disk cache recovers little of it** for climate runs: warm 3×3 is only 12% faster than cold overall (289 vs 328 s; weather 170 vs 206 s), and the default scenario's weather still takes 18 s warm. The remaining cost is SQL computation (CMIP6 baselines and deltas, rolling windows, per-member bounded collects), not remote fetch. An Rprof of the warm default-scenario weather call (≈20 s, pipelines excluded) attributes **8.5 s (41%) to forced `gc()`** — one full collection per CMIP6 member and per period in the bounded collection path (`fct_get_weather.R:1864, 1898`) — 7.6 s to DuckDB execution (5.9 s materialisations, 2.7 s collects) and 2.2 s to dbplyr SQL rendering. The built-in `WISEAPP_WEATHER_PROFILE` table accounts for only 5.6 s of those ≈20 s, so it cannot find this. Cold, the ERA5 read (8.4 s) and the H3 mapping read (3.0 s) add the remote part.
2. **Worker-side partial aggregation costs 21% of the OLS 3×3 run** (70.7 s): every completed SSP × period group runs the full 9-method suite so `mod_2_02` can be seeded. That is the right trade for responsiveness only if the main process then never repeats it; methods or controls that are not seeded still cost up to 51 s on the main process.
3. **The result artifact is the memory problem.** 521 MB (OLS) and 1.03 GB (RIF) for BFA, read back on the main process (3.5–6.1 s), and the worker peaks at 6.4–6.8 GB. For IRN (≈40× the households) this does not fit; the tracking log already notes "IRN 3×3 hits 16 GB".
4. **RIF snapshots cost 3.8 s of main-thread serialisation** before the job is even submitted (the full `model_fit`, plus `mf$fit3` again as `fit_multi`).

### 10.4 Posit Connect settings and operations

The current runtime settings (guidelines §10: max processes 8, max connections per process 1, load factor 0.5, idle timeout 60 s, no RAM limit) interact with the findings above:

- With **1 connection per process** the synchronous stages no longer freeze other users, but every process now holds the main R process, a mirai dispatcher and a daemon, each with its own in-memory DuckDB that defaults to 80% of RAM, and no `memory_limit`, `temp_directory` or `threads` is set (CR-PERF-13). The BFA worst case alone peaked at 6.8 GB in one process; at 8 processes the host has no protection against OOM, and an OOM kill of the daemon then hangs the process (R2-OPS-06).

## Appendix B: Method, scripts and data handling

- **Reading.** Every file in `R/`, `inst/app/www/custom.{js,css}`, `inst/app/vendor/hexmap.js`, `tests/`, `batch/`, `dev/`, `app.R`, `DESCRIPTION`, `NAMESPACE`, `manifest.json`, `.Rbuildignore`, `.rscignore`, `.gitignore` and `inst/golem-config.yml` was read in full, split by pipeline area across parallel read-through passes, and every High finding carried into §1.1 was re-checked against the code by hand. The Step 0 → 3 path was traced call by call (summarised in §5.1).
- **Profiling.** Step 0–1: one script per repetition reproducing the module call chains (`mod_1_02` load chain, `mod_1_05` weather call with the 30-year window, `mod_1_06/07` LASSO and fit). Step 2: `step2_async_worker()` driven in-process with `trace()` timers on `get_weather`, `run_sim_pipeline`, `step2_display_aggregation_suite`, `step2_compute`; main-thread costs (`serialize()` of the snapshot, `qs2::qs_read()` of the artifact, the Results suite) timed separately. Step 3: the `mod_3_06` run sequence and the Results/decomposition reactives called directly. Step 2 Results UI: `testServer(mod_2_02_results_server)` with flushes timed. Rprof on the weather stage and Step 1 blocks. Peak RSS: process tree sampled every 0.25 s from `/proc`. Two or more repetitions per case, each in a fresh process; medians reported with ranges where they differed materially.
- **Repository harness.** `dev/bench_step2.R` was run once on BFA through a scratch copy patched only to accept a Databricks connection. Its timings were not used (R2-OPS-08).
- **Prototypes.** All in the scratch directory, never in the repository: a `get_weather()` copy without the two forced `gc()` calls; a `get_weather()` copy with a pooled CMIP6 baseline; matrix-encoded chart series; a larger aggregation preparation cache; `split()` vs `which()`. Equivalence was checked with xxhash64 digests of predictions and factor loadings, or parsed-JSON equality.
- **Data handling.** Microdata stayed in memory or in temporary files under the session scratch directory; those files (fitted-model and result snapshots, weather disk caches) were deleted at the end of the review. No household-level values, ids or small cells were written to the report, commits or chat. Credentials were read only from the environment by the app's own code and sent only to the configured Databricks host; they were never printed. During one profiling script, an unintended auto-print sent a few rows of the location-level H3 table (H3 cell ids, location ids and cell population — no household data) to a local tool log of this session; it was not written to the repository or the report.
